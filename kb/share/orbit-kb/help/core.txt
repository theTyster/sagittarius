orbit-kb help core: facts, attestation types, and queries that every KB has

Write facts with: orbit-kb add "claim(c1, introduce, 'Primary buttons are purple.')"
Quote text with single marks. Do not edit kb.pl by hand.

Facts
  request(Id, Text)              the human's words, word for word
  claim(Id, Label, Text)         Label is preserve (true now, must stay true),
                                 retire (true now, must become false),
                                 or introduce (false now, must become true)
  cites(Claim, Text)             the request text that the claim serves
  example(Claim, Text)           a concrete case of the claim
  supersedes(New, Old)           New replaces Old. Never edit a claim or a hypothesis.
                                 Both are claims, or both are hypotheses (discovery).
                                 Nothing can replace itself, also through a chain.
                                 add refuses it, and lint reports E15.
  universal(Claim)               the claim is about every input; it burns (orbit-kb help build)
  check(K, Claim)                K is an executable check of the claim. A check never moves:
                                 for a claim that replaces it, add a new check (lint W5).
  world(Fact), source(Fact, Where)   the current state, and where you saw it.
                                 A fact that you did not record is false.
  question(Q, Claim, Text), assumed(Q, Default), answer(Q, Answer, By)
  due(X, 'TIME')                 claim, check, or question X is due at TIME. While X is open
                                 after TIME, blocking(past_due(X)) holds.
  ticket(S)                      subject S holds the ratified ticket
  scope(in|out, Text), risk(Id, Text), assumption(Id, Text), not_explored(Text)
  note(X, Text)                  a note about an existing id X (a claim, a question, r1).
                                 It does not create an id.

Artifacts and records
  orbit-kb subject s1 PATH       record an artifact and compute its digest
  orbit-kb attest TYPE SUBJECT 'PREDICATE' [--by human|agent]
  Never type a digest. Put it through the shell:
    D=$(orbit-kb subject M PATH)   then use '$D' in the fact.
  The predicate digest(current) means the recorded digest of the subject.

Attestation types
  disclosure   guess(Q) | unverified(Text) | disagreement(Text) | out_of_scope(Text)
               | self_error(Text) | other(Text)                      agent or human
  divergence   claim(C) | hypothesis(H) | model(M)                   human or agent
               Put the description in a note.
  disproof     verdict(C, refuted(Text) | inconclusive | abstained)  agent
               Put the counterexample in the text of refuted.
  approval     digest(current)                                       human only
  test_result  written by orbit-kb run only

Queries (orbit-kb query 'current(C)' -n 0)
  current(C)         claim C is not superseded
  defeated(Q)        a human answer differs from the default of Q
  to_ask(Q)          Q is unanswered, no human waived it, and its claim is current and contested
  contested(C)       one or more divergences name C
  contested_twice(C) two or more divergences name C
  refuted(C)         a verdict says that C is refuted
  passed(K)          the latest run of K passed
  was_red(K)         K failed before it passed
  stale(A)           approval A is for a digest that is no longer current
  blocking(X)        X blocks done: to_ask(Q), burn_open(C), flare_open(C), under(C), over(X),
                     check_failing(K), check_unrun(K), waiver_lapsed(W), past_due(X),
                     supersede_cycle(C), no_claim. orbit-kb show blocking prints each with its text.

Local rules go in rules.pl beside kb.pl. They cannot change done, or the burn and flare
rules (lint reports E16). not p means that p has no answer (negation as failure), so
not under(_) means "no under at all". A predicate must not depend on itself through not
(lint E18). There is no classical negation: a fact that is not recorded is false.
If the schema does not fit, add a fact of a new predicate. Its first use declares it
(orbit-kb help add), and lint lists it (W7) for review, and flags a name that looks like a
typo of a declared one (E19). declare is optional: use orbit-kb declare ... --doc TEXT
before the first use to give the predicate a doc and types.

Rules for the KB
  Size the KB to the work. A small change needs a few facts: the request, one claim, and one
  check. Write a fact only if a query or the delivery report reads it.
  Put the KB where it is useful. Commands find it from --dir, then $ORBIT_KB, then the nearest
  parent directory that holds one. Do not commit the KB or its runs/ logs unless the human
  asks: the delivery carries the evidence.
  When the work moves to the other orbit, add its module (orbit-kb uses build, or orbit-kb
  uses discovery), then run orbit-kb lint. The new module can add findings.

DECOMPOSE: claims and questions
  Every move reads the ticket text itself, so that an error in an earlier move does not pass on.
  1. Split the ticket into claims. Give each claim one label (preserve, retire, introduce).
  2. Each claim cites the ticket text that it serves. A claim with no citation is drift. Drop
     it, or propose it to the human as a ticket change.
  3. For each claim, record the questions that a careful reader would ask, each with your
     default answer (assumed). These questions stay dormant: asking them all now would bury
     the human in questions that may never matter. A question becomes to_ask when its claim
     is contested.
  4. Restate each claim as one or more concrete examples, for example "Submit on /checkout
     renders #6B3FA0". The human reads examples. The human never has to read formal text.
  5. Mark a claim visual when the human must see the result to judge it (orbit-kb help build).

Asking the human
  Build on your default assumptions, unless a wrong default is costly or impossible to undo
  (data loss, external effects, public interfaces, security, or money), or two defaults are
  equally likely and the build is large. Then ask before you build:
  - Ask at most three questions in one round. Choose them in this order. First, the questions
    whose default is the most costly if it is wrong. Then, the questions whose answers also
    settle other questions. The rest wait for the next round.
  - Give concrete options, and mark your default.
  - Do not ask the human to approve a list. A long list invites "approve all", and that is a
    quiet failure.
  In discovery, see also orbit-kb help discovery (ASKING).

Speed
  Run independent tool calls in parallel. Give long mechanical work (wide searches, long test
  runs) to a subagent on a fast model. A small task does not need a subagent.
  Report results, not process.
