orbit-kb help build: the build module (orbit-kb uses build)

Facts
  change(X, Text)       a change that you made
  serves(X, Claim)      the claim that change X serves
  burn_requested(Claim) the human asked for a proof
  visual(Claim)         a human must see the claim to judge it (a look, a layout, a name);
                        mark it at DECOMPOSE, or when the human asks to see it
  demo(Subject, Claim)  a screenshot or a recording (orbit-kb subject) shows the claim
  ac(Claim)             the claim is an acceptance criterion (AC) of the ticket. It changes no
                        rule: show blocking and draft blocking name an unmet AC as such
  conformance(Check)    an optional check that runs the code against the Lean model
  change_at(X, Time)    when change X was recorded; add writes it with change(X, Text),
                        and actor(X, Role, Session) too (orbit-kb help core). add refuses it

Attestation types
  lean_result   stated | refuted(Counterexample) | tested(N)    progress on a Lean model
  lean_proof    written by orbit-kb prove only
  waiver        human only: waive(Target, 'DUE', 'REASON')

Queries
  fulfilled(C)  a check of C passed; for retire and introduce, it failed first; C is not refuted
  under(C)      current claim C is not fulfilled, and no human waived a check of it
  over(X)       change X serves no claim
  independently_verified(C)
                an upheld verdict on C, by an actor whose role and session both differ from
                the actor of the last change that serves C, after that change, rests on a run
                of a check of C by the same actor after that change. done does not read it;
                lint warns (WR1) on each current claim without it, in a KB that records actors
  done          at least one claim is current, nothing is under, nothing is over,
                nothing is to ask, no burn or flare is open, and no claim is in a supersede cycle.
                A KB with no current claim is not done. whynot done then says
                "no claim is current".
  burn(C)       C is contested twice (and not visual), is universal, or the human asked
                for a proof; or C supersedes such a claim, directly or through other claims
  burn_open(C)  current claim C burns, and has no proof that still counts and no waiver
                before its due time
  flare(C)      C is visual, or C supersedes a visual claim, directly or through others
  flare_open(C) current claim C flares, and no human approved a demo of it at the demo's
                current digest, and no waiver is before its due time

SURVEY: close the world (build)
  1. Record as world facts the current behavior that the claims rest on. Under the
     closed-world assumption, a fact that you did not record is false. So record the slice
     that the ticket touches, and nothing more.
  2. For a defect, reproduce it first. If you cannot reproduce it, or the feature already
     exists, stop and tell the human.
  3. Skip SURVEY when discovery ran. When the change site is obvious, skip step 1, never step 2.

PIN: when the request or a question has an owner (the tracker or the ledger)
  1. The request is a tracker item: start with orbit-kb init DIR --request-file F --source REF
     (F holds the item as you read it, plain text or its JSON). Read the item again before
     done and after each handoff: orbit-kb pin-request --request-file F. A changed text blocks
     done until a human accepts it (pin-request --accept --by human).
  2. A question that waits only on the hub owner: orbit-kb pin-question Q ledger ASK. Any other
     question that a person must answer in the tracker: orbit-kb draft questions, the human
     posts it, then orbit-kb pin-question Q tracker ITEM. The answer comes back with
     orbit-kb pin-answer Q ITEM --text-file F --by NAME.
  3. Never copy a request or an answer by hand: pin it.

BUILD: checks first
  1. Write the checks first, from the claims and the examples. Add a screenshot check when
     the change has a user surface.
       orbit-kb add "check(k1, c1)"
       orbit-kb run k1 -- npm test -- button     run it; the output goes to runs/N-k1.log
  2. Run each retire and introduce check against the current code first. It must fail.
     The red run proves that the check can fail. Run every check with orbit-kb run.
  3. Build the change. Change only what the claims need. Record each change and the claim
     that it serves: change(X, Text), serves(X, Claim).
  4. Do not edit a check to make it pass: that hides a divergence. If a claim was wrong, add
     a claim that supersedes it, and disclose the change.

FULFILL: fulfillment in both directions (verify)
  Review with fresh eyes. Prefer one subagent with a fresh context. This is its brief:
  - It sees only the ticket, the KB, and the diff. It does not see the builder's reasoning.
  - It works under its own role and session (its first write takes the writer lock):
      orbit-kb review start --as review --ticket TICKET.md --diff BASE..HEAD
    This records what it saw: the ticket, the KB stamp, and the diff (review_saw).
  - It reruns every check of each claim itself:
      orbit-kb run --as review k1 -- CMD
  - It records one verdict for every current claim, with what it tried, and the runs that
    the verdict rests on:
      orbit-kb attest disproof c1 "verdict(c1, upheld('what I tried'))" --as review --rests-on a12
    upheld(Text), refuted(Text), inconclusive(Text), or abstained(Text).
  - It reads orbit-kb report (the Review section: reviewer, verdict, reruns) and orbit-kb
    lint: WR1 names each claim that is not independently verified (independently_verified).
  - Under: orbit-kb query 'under(C)'. Each answer is a claim that is not fulfilled.
  - Over: orbit-kb query 'over(X)'. Each answer is a change that serves no claim. Remove it,
    or propose it to the human.
  - Open questions: orbit-kb query 'to_ask(Q)'.
  - Clean up: keep a test only if it guards a claim, records a human answer, or reproduces a
    fixed defect. Delete the other tests that you wrote.
  The build is finished when done holds (orbit-kb show blocking lists what blocks it). Stop
  there. Do not polish beyond the claims.

DISPROVE (verify, and in discovery): before you deliver a burned claim, or when you doubt any
claim, try to break it within a small budget. Record one disproof verdict (orbit-kb help core).

Burns: prove the claim in Lean
  A statement with sorry is not a proof. "No counterexample in N trials" is not a proof.
  1. Write a Lean model of the behavior. State the claim as a theorem.
  2. Add #eval examples. Show them to the human as a table.
  3. Search for a counterexample (for example Plausible) before you prove.
     If you find one, record lean_result with verdict(C, refuted('THE CASE')) and ask the human.
  4. Prove the theorem. Then: orbit-kb prove C FILE THEOREM
     It records the proof only if the theorem has no sorry, no native_decide, and no
     axiom of its own, and if the kernel accepts it again. Nothing else records a proof.
  5. Read the statement that prove prints. Check that it says what the claim says.
     orbit-kb cannot check that. Show it to the human.
  6. Carry the result back to the code. The proof is about the Lean model, not the code.
     Each Lean example becomes a test case.
  A claim that supersedes a burning claim needs its own proof.
  A change in a Lean file of the project, or in a Lake file, reopens the burn.
  A change inside a path dependency (a shared library) does not.

Flares: show the claim to the human (burns get proved, flares get shown)
  A visual claim needs a human to see it, not a proof. A claim can burn and flare at once
  (a contrast ratio and a look): prove the invariant, and show the look.
  1. Make the demo: a screenshot, a recording, or a before and after.
  2. orbit-kb subject s1 shot.png
     orbit-kb add "demo(s1, c1)"
  3. Show the demo to the human. Only the human approves it:
     orbit-kb attest approval s1 'digest(current)' --by human
  A new file under the same subject makes the approval stale, and the flare opens again.
  An edit of the demo file on disk reopens it too, even before orbit-kb subject runs.
  Contests on a visual claim do not make it burn. They keep its flare open.
  A preference change (a new name or color, and no one misread the intent) is a new claim
  that supersedes the old one. It is not a divergence.

When the human says it is wrong (a divergence, not a preference change)
  1. On the light path, shift up now: start a KB, and record the request, your claims, and
     the checks so far.
  2. Record a divergence on the claim: orbit-kb attest divergence C 'claim(C)', and a note.
  3. Decide which is wrong: the build, or the problem itself. If the problem is wrong, run
     orbit-kb uses discovery, and go back to discovery (orbit-kb help discovery, BACK).
  4. Record the human's answer: answer(Q, Answer, human). Defaults that conflict with it are
     now defeated.
  5. Query to_ask(Q). Ask that small cluster, not every dormant question.
  6. Rebuild, and run the checks again. If burn(C) now holds, prove the claim in Lean (Burns).
  The KB already holds the questions, so you continue from where you stopped.

Waivers (the human only; the human sets the due time)
  orbit-kb attest waiver C "waive(C, '2026-11-30T17:00:00Z', 'why')" --by human
  C is a claim (its proof and its demo), a check, or a question.
  Until the due time the item does not block done. A waived check covers its claim,
  but the claim is not fulfilled. After the due time the item blocks done again.
  report lists every waiver. The delivery says "not proved" for a waived burn, and
  "not shown" for a waived flare.

Verdicts for disproof (orbit-kb help core): upheld(Text), refuted(Text), inconclusive(Text),
abstained(Text). Name the runs with --rests-on.
Do not weaken a claim to absorb a counterexample. Record it, and ask the human.
