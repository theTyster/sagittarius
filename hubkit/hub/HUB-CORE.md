# HUB-CORE.md: the shipped rules of the hub

This file ships with the hub template. **Do not edit it.** An upgrade replaces it. Put this hub's
own rules and changes in `CLAUDE.md`, which imports this file. Where the two disagree, `CLAUDE.md`
wins.

## The hub exists to enable throughput

1. More solutions. 2. Faster. 3. Better quality. An agent may measure (2). The humans define (1) and (3).

The hub is read mostly by **agents**. Write for an agent that just booted with no memory: state
facts, name paths, give dates.

## What lives where

An agent that just booted looks here to know where each thing lives. The hub has seven stores. Each
fact kind has one owner. Other stores may pin it (a copy with a digest) or read it. The tables
below are generated from the design: do not edit them by hand
(`python3 hubkit/tools/storemap.py --write` makes them from `hubkit/tools/store-facts.json`).

Owner is the store that holds the fact and decides it. Pinned in: a store that keeps a copy with a
digest. Read from: a store that reads it by query. Copied in: a store that shows a rendering of it
for governance. `outside` is a home outside the hub.

### The copy rule

The tracker owns a ticket's text and state; the hub holds a **pointer** (`issue:123`) and the flow
state around it. A **pinned copy** (the item's text with a digest, in the project KB: `orbit-kb
pin-item`) is allowed. It goes **stale** when the source has a later pin. An **unpinned copy** is
not allowed: a second copy with no digest diverges, and nothing says that it did. **Re-pin a
tracker item each time an agent reads it for a ticket**, so the digest names what the agent read.
The spec KB holds what a ticket needs and pins the rest: do not copy all context into it.

### Where a spec KB lives

A spec KB has the ticket's clock, not the week's. It lives at `specs/<slug>/` at the hub root,
outside W0 to W5, and the flow db refers to it as `kb:<slug>` (`hubflow.py where <slug>` prints the
path; `orbit-kb show open` there says what is left). Only the spec KB decides what blocks. A hub
made before 0.3.0 keeps spec KBs at `W*/analyses/<slug>/kb`; that form still resolves (UPGRADING.md
says how to move them). In a hub the spec KB is committed, with the hub: git is the archive, and
`orbit-kb help core` names this as the exception to "do not commit the KB".

### What a week holds

A week holds only what people gave it: raw reports in `W*/reports/` and meeting transcripts in
`W*/transcripts/`. There is no `analyses/` slot: analyses are written in the project KB when they
are made. The project KB pins the digest of a report or transcript only when a lasting project
fact relies on it. `hubflow.py index-transcripts W0` parses the week's meeting transcripts (`.md`,
`.txt`) and Claude Code transcripts into the ledger: `transcripts` for the summaries, `--detail ID`
for the turns, `--grep TEXT` for the turns that say TEXT with file and line, and the file last.
`rotate --yes` rebuilds that index, so a retired week's rows go with it. Rotation never retires a spec KB. A spec KB whose ticket is closed is a triage
item at rotation: the decision is archive, capsule, keep or escalate, recorded once with
`hubflow.py spec-triage`. Archive is `git rm -r specs/<slug>`; history keeps it.

### Outbound: one home per thing

A staged edit to a tracker item is a `draft/4` in the project KB (`orbit-kb help draft`). Free
outbound text (mail, chat) is drafted in `W0/outbound-staging/`. A tool posts nothing: a human sends.
To attach the spec KB to a tracker item, `orbit-kb draft attach` prints the file and the line to
paste, and a human attaches it. After sending, the human (or an agent that the human told) records
`pushed/2`.

### Bespoke tools

A tool, skill or small store an agent makes is listed in `TECHNOLOGIES.md` (or the memory file the
hub names) only if other agents can use it for other tasks. A per-ticket helper stays with its
ticket. A tool is unused when there is no pin from an open spec KB and no listed use since the last
rotation. Only unused tools are pruned, at rotation, each with a triage decision. A model or
proof that an open spec KB pins is never pruned.

### Who owns what, outside the stores

SOP is owned outside the hub, and the build does not need it. Product rules live in the project KB
(`orbit-kb help project`), and a spec pins the ones its claims rely on. The repos of the project and
how they connect are in the project KB; the repo map is `kb/bin/repo-map` (see its README for the
formats).

## Without orbit-kb (the informal release)

The informal release is this hub with only the five informal stores: `ledger`, `memory`, `weeks`,
`bespoke` and `tracker`. It needs Python 3 and git, no Prolog and no Lean. It has no spec KB and no
project KB. What changes:

- **Nothing blocks from a spec KB.** Triage is the agent's: `triage ID keep|lapse|capsule --note T`
  acts at once, and `triage ID escalate --note T` leaves the item open at the top of `view open` for
  the human. `rotate` lists the due items under `untriaged:` and the escalated ones under
  `escalated:`, and exits 0 when each due item has a decision. `check` exits 0 when the db and the
  JSONL agree. `spec-triage` has nothing to do: there is no `specs/`.
- **Do not add `kb:` refs.** With `HUBFLOW_ORBIT_KB` unset and no `orbit-kb` on the PATH, hubflow
  cannot ask a spec KB, so an item with a `kb` ref is treated as blocking (fail-safe): an agent's
  keep or lapse of it becomes escalate, and only a human closes it (`--by human --note`).
- **Pointers only.** With no project KB there is no pinned copy: the hub holds the pointer
  (`issue:123`) and no copy of tracker text. All outbound text, a tracker edit too, is drafted in
  `W0/outbound-staging/`. A human sends.

Where the informal release keeps each fact kind that the spec KB or the project KB owns (generated
with the map above; `not kept` means the informal release keeps no record of it):

## Panes

The panes of `prompt/PANES.md` (review, discovery, build) are the roles that make and judge. Each
runs as a named session that the human sets up outside the hub (for example in dotfiles);
`flow/seed.json` gives the hub the names. Verify is review's: a hub with no review session gets
its verify from a fresh-eyes subagent that records its verdicts in the spec KB. A handoff between
panes is one `hubflow.py handoff` row plus the KB, as `prompt/PANES.md` says.

## Structure: the hub is a calendar

```
CLAUDE.md                                   this hub's own rules; imports the files below
HUB-CORE.md  PRINCIPLES.md                  always in context: the shipped rules, the principles
HEURISTICS.md  TECHNOLOGIES.md              always in context: this hub's own memory files
.hub-template.json                          the template version and the checksums of shipped files
.claude/skills/                             hub-rotate, hub-flow (each may have a LOCAL.md)
.claude/scripts/hubflow.py                  the only writer of flow/flow.db
flow/                                       flow.db (ignored), seed.json, jsonl/ (tracked)
specs/<slug>/                               one spec KB per ticket (the ticket's clock, not the week's)
W0/ … W5/                                   the current week … five weeks back: reports/, transcripts/
```

Six weeks on disk, no more. Older weeks exist only in git history: that is the archive. Weeks start
Monday. Every week dir has a `WEEK.md` whose first line is its date range. Rotate with the
`hub-rotate` skill at the first session of the week.

Before you drop something, ask: **is it durable?** Durable knowledge is promoted out of the week
dirs (a root file, a skill, the project KB), never left to roll off.

## Flow state lives in the db

Asks to a human, in-flight threads, holds and handoffs between sessions are rows in `flow/flow.db`,
written only by `hubflow.py`. Load the `hub-flow` skill before any write. Each session has an
identity (`HUB_SESSION`), set where the session is started. Named sessions are set up outside the
hub; the hub knows only their names (`flow/seed.json`).

## Shipped files and local changes

- `.hub-template.json` lists the shipped files. Do not edit a shipped file to change a rule; put
  the change in `CLAUDE.md`, or in a `LOCAL.md` next to a skill's `SKILL.md`.
- A shipped file can still be edited when there is no other way. `hubkit.py status` then shows it
  as modified, and the next upgrade merges the release into it instead of replacing it.

## Auto-memory is disposable

Write memories freely. Within one month each one is either promoted into the hub (a heuristic, a
skill, a root file) and deleted, or just deleted. A memory is never the record of a finding.

## Hard rules

- Commit the hub at natural stopping points without being asked. Stage explicit paths, never
  `git add -A`. Commit with a pathspec (`git commit -m … -- <paths>`), so a peer session's staged
  files do not ride along.
- Outbound text is staged, never sent by an agent: a tracker edit as a `draft/4` in the project KB,
  other text in `W0/outbound-staging/`. A human sends.
