# hub-flow: the flow-state db

**Local changes:** if `LOCAL.md` exists next to this file, read it now. It holds this hub's changes
to this skill and wins where the two disagree. Do not edit this file: an upgrade replaces it.

`flow/flow.db` holds the **flow state** around work, never the work itself. A ticket's body, its
criteria and its column stay in the tracker; an item holds a pointer (`issue:123`, `pr:45`) and who
it waits on. Which store holds what is in `HUB-CORE.md` ("What lives where").

**The copy rule.** A pinned copy of a tracker item (its text with a digest, in the project KB) is
allowed. It goes stale when the source has a later pin. An unpinned copy is not allowed. Re-pin a
tracker item each time an agent reads it for a ticket.

**Outbound has one home per thing.** A staged edit to a tracker item is a `draft/4` in the project
KB; free outbound text (mail, chat) is drafted in `W0/outbound-staging/`. A human sends; afterwards
the human (or an agent that the human told) records `pushed/2` in the project KB. Nothing is posted
by a tool. `.claude/scripts/hubflow.py` (`$HF` below) is the only writer. Every write also rewrites
`flow/jsonl/*.jsonl` in the same transaction; git tracks the JSONL, the db file is ignored.

## Who you are

Every write needs a session identity: `HUB_SESSION` (set where the session is started, outside the hub) or `--session S`.
No identity → exit 1. `--by human` only records a human's own words and needs `--note "<quote>"`.

## Kinds

| Kind | Id | Use it for |
|---|---|---|
| `ask` | A- | a question or decision that waits on a person (`--waits-on`) |
| `thread` | T- | a live problem this session is carrying |
| `hold` | K- | something deliberately paused; `park --until` keeps it off the triage list |
| `handoff` | H- | work passed to another session (`handoff --to`) |
| `summary` | S- | a short note of a meeting transcript you read (see Transcripts); it lapses by itself |

Statuses: `open`, `waiting`, then `done`, `dropped`, `lapsed` (closed).

## Read first

```
$HF view v_inbox --session $HUB_SESSION    # mine, unaccepted handoffs first
$HF view v_waiting_on --person me           # what waits on a person
$HF view                                    # open items, escalated ones (waiting on the human) first
$HF view escalated                          # what only the human can decide
$HF view v_stale                            # idle ≥14 d (warn), ≥28 d (lapse_due: due for triage), handoffs unaccepted >1 d
$HF view v_dup_refs                         # one ticket on several open items: merge or link them
$HF show A-0007                              # one item, with its events
$HF sql "SELECT …"                           # read-only; one SELECT/WITH only
$HF transcripts [--detail <session id>]     # the Claude Code session index: summary, then user messages
$HF transcripts --files                     # the week transcript files, each with its transcript: ref
```

Read at session start and after every compaction: the db is the memory, not the conversation.

## Write

```
$HF add ask --title "…" --waits-on me --ref issue:123 [--analysis <slug>] [--note "…"]
$HF add thread --title "…" --ref pr:45
$HF handoff --to build --title "…" --ref issue:123 --note "where to start"
$HF accept H-0003                 # only the receiving session can accept
$HF renew T-0002 --note "still live: next step …"
$HF park K-0001 --until 2026-12-01 --note "why"
$HF close A-0007 --reason done|dropped --note "…"
$HF reopen A-0007 --note "…"
$HF ref A-0007 add issue:124 ;  $HF link T-0002 T-0005 duplicates
```

The writing session owns what it adds, so it shows in that session's inbox. Pass `--owner <session>`
to give it to another session, or `--owner none` to leave it unowned (no inbox shows it).

**Asks.** An ask that waits only on the owner (seed key `owner`, else the person `me`) is owned
by this ledger. An ask that waits on another person is owned by the tracker: give it the `issue`
ref of the tracker item. `$HF check` flags an ask to another person with no issue ref (exit 3).

Rules the script enforces: `issue` and `pr` refs are digits only; `--analysis` takes the slug of a
spec KB, never a `W0/…` path. A spec KB lives at `specs/<slug>/` and its ref is `kb:<slug>`;
`$HF where <slug>` prints the path (an old hub's `W*/analyses/<slug>/kb` still resolves).

**A handoff** is a `handoff` row plus the KB. The one procedure is written in `PANES.md` (installed as
`~/.claude/sagittarius/PANES.md`; `prompt/PANES.md` in the Sagittarius checkout)
("Handoffs in a hub"): follow it, and do not restate it here. A row nobody was told about is a
silent handoff.

## Ageing and triage

No work item lapses by itself. An open item not renewed for 28 days, and not parked through today, is
**due**. At a rotation each due item needs one recorded disposition, and `rotate` exits 1 and lists
the `untriaged` items until each has one:

```
$HF triage A-0007 keep     --note "why it still matters"      # renews it
$HF triage A-0007 lapse    --note "why nobody needs it"       # closes it as lapsed
$HF capsule A-0007 --summary "the context the tracker lacks"  # then:
$HF triage A-0007 capsule  --note "context is in the capsule" # renews it
$HF triage A-0007 escalate --note "only the human can decide" # stays open, top of `view`
```

An agent may triage. An item with a `kb` ref to a spec KB that blocks is not the agent's to end:
an agent's keep, lapse or capsule of it is recorded as **escalate**, and an agent's `close`,
`renew`, `park`, `set --status` or `ref rm kb:…` of it (or of any escalated item) is refused. hubflow asks `orbit-kb --dir <kb dir> query 'blocking(X)'` (`HUBFLOW_ORBIT_KB` names
another command). If the query fails, orbit-kb is missing, or the kb dir is in neither `specs/` nor
W0–W5, the item counts as blocking. An escalated item stays open at the top of `view`, with no automatic action,
until the human records a disposition (`--by human --note "<their words>"`).

**Capsules** hold what the tracker lacks: a summary (at most 1000 characters), the hub's
`git rev-parse HEAD` and the item's `kb` and `file` refs. `$HF show ID` prints the newest capsule
first. Never copy a ticket's own events into a capsule: they stay in the tracker.

**A human skip:** `$HF close ID --reason human_skip --by human --note "<their words>"` also closes
the open items linked to ID by `blocks`, records why on each, and prints a `waiver:` command for each
blocking item of each linked spec KB. hubflow never writes to a spec KB: show the human the
waivers; the human sets the due time and runs them.

**A waiver from the KB side:** after the human runs a waiver in a spec KB (from a hub skip, or on their
own), run `$HF skip-waived`. It parks each open item whose spec KB is clear only because of a live human
waiver, until the date of the waiver's due time, with the waiver in the note; after that date the item
is back, and blocks again if the KB does. It never drops an item, and an escalated item stays for the
human. You need not remember it: `$HF check` prints `skip_waived: <ids>` when there is something to
park, so run it when check names an item, and at the start of a session.

Items closed more than five weeks before the rotation are pruned; the JSONL history in git keeps
them. The `hub-rotate` skill runs `rotate`.

## The spec KB of a closed ticket

A spec KB at `specs/<slug>/` whose every item is closed is a triage item at the rotation. `rotate`
lists it as `spec_kbs_untriaged:` and exits 1 until each has one decision, recorded once:

```
$HF spec-triage <slug> keep     --note "why the KB stays"
$HF spec-triage <slug> capsule  --note "context is in the capsule"   # needs $HF capsule ID first
$HF spec-triage <slug> escalate --note "only the human can decide"
git rm -r specs/<slug> && $HF spec-triage <slug> archive --note "why"  # history keeps it
```

An agent's decision on a spec KB that blocks is recorded as `escalate`.

## Transcripts

`$HF index-transcripts W0` reads the Claude Code JSONL transcripts under a week dir into the
ledger: per session the first and last time, the first user message, message and tool counts,
and the path; plus each user message cut to 200 characters. It never stores a whole transcript,
and a rerun gives the same rows. Read `$HF transcripts` first, then `--detail <id>`, then the file
itself only if you still need it. `rotate --yes` rebuilds this index from W0..W5, so a retired
week's rows go with it.

Code never parses a meeting transcript. When you read one, put what is needed into the ledger
yourself: open work as normal items (asks, threads, holds, handoffs), a short `summary` row, or
what else you judge useful. Point each one at the transcript with a `transcript:` ref: the file
name and its sha256, which `$HF transcripts --files` prints for each file in `W*/transcripts/`.
The ref still works after a rotation moves the file: `$HF transcripts --find NAME@sha256:HEX`
prints where the file is now, and exits 1 when the file changed or left the hub. Decisions and lasting facts go to the project KB, not the ledger.

```
$HF add summary --title "Standup 11-02: the conveyor date, the test rig, two open questions" --ref transcript:standup.md@sha256:<hex>
```

A `summary` row is not work. It is never due and never blocks `rotate`: the first rotation when it
is 28 days old (counted from when it was added) lapses it, and lists it as `lapsed:`. It is then
pruned like any closed item.

## Exit codes

0 ok · 1 bad input or a refused rule (read stderr) · 2 db state (missing, exists, older or newer
schema, locked) · 3 `check` found the db and JSONL disagree, or an untracked ask to another
person. Exit 2 is never "no".

## Recovery

`$HF check` compares the db with the JSONL. If the db is lost or broken: move it aside, then
`$HF rebuild` recreates it from the JSONL.

## After a template upgrade

If a command says the db has an older schema, run `$HF migrate`. It copies the db to
`flow/flow.db.bak-v<N>`, runs the steps, and rewrites the JSONL. Then run `$HF check`, and commit
`flow/jsonl/`. A JSONL written by an older schema does not `rebuild` with a newer script: rebuild
with the older script, then migrate.
