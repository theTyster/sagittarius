A briefing for the human

Your hub: shared memory for a small team of AI sessions

A few long-running Claude Code sessions share one git repo as their memory. It forgets on a schedule, keeps what matters, and tracks who is waiting on whom in a small database. This page explains what you get, what you do, and what to say to your agents.

The idea in four parts

Each part solves one way that long-running agent work goes wrong.

1

It forgets on purpose

Only six weeks of notes stay on disk. Older weeks live in git history. Agents stop tripping over stale context.

2

It keeps what is durable

Lessons, rules and tool facts move into a few files that every session always reads. Nothing durable ages out.

3

Tickets stay in your tracker

The hub holds pointers like issue:123, never copies. One home per fact, so nothing disagrees.

4

Who-waits-on-whom is a database

Open questions, live threads and handoffs are rows, not prose. Views answer “what is waiting on me?” in one line.

The database

One small SQLite file, flow/flow.db. One script writes it. Git keeps a readable copy of every change.

Ask waits on a person

An agent needs a decision or an answer from you.

Thread

A live problem a session is carrying.

Hold

Paused on purpose, with a date it comes back.

Handoff

Work one session passes to another. The receiver must accept it.

How an item lives and ends

Opened

With a pointer to the ticket and who it waits on.

→

Renewed

Someone confirms it still matters, with a next step.

→

Closed done / dropped

Or lapsed: 28 days with no renewal.

→

Pruned

Five weeks after closing. Git history keeps it.

Lapsing is the point: if nobody renews an item for four weeks, it is probably not live. Before it lapses, it shows up as stale, so you get a chance to keep it.

The sessions

A few named sessions, each in its own terminal pane, each with one job. Rename them to fit your work.

SessionIts job (example)
discoveryTurns reports and vague requests into clear tickets.
buildBuilds, tests and reviews changes.
processImproves how the work itself is done.
supportEverything human-facing: meetings, messages, reports, drafts for you to send.

Each session is started with sessions/launch.sh <name>. It picks up the same conversation as last time and tells the database who is writing. Sessions pass work with a handoff row plus a direct message, so nothing is passed silently.

Your part

About ten minutes a day and one rotation a week.

D

Daily

Ask what is waiting on you. Answer, renew, or drop each item. Short answers are fine.

M

Monday

Tell one session to rotate the hub. Read what lapsed and keep anything that still matters.

!

When something is wrong

Say so plainly (“that is not what I meant”). That disagreement is the most useful signal the agents get.

✉

Outbound

Drafts wait in outbound-staging/. You read, edit and send. Agents never send for you.

Taking updates

Your hub is yours from the first day. New releases of the template come in without overwriting your changes.

1

Your files

CLAUDE.md, HEURISTICS.md, the session list and your notes belong to your hub. An update never changes them.

2

Shipped files

The shipped rules (HUB-CORE.md), the scripts and the skills. If you did not change one, an update replaces it.

3

Your changes to shipped files

Your agent applies the release's change by its intent, keeps your edits, and shows you the diff before it commits.

✓

Proof

The agent runs the tests (including the deliberately broken copies) and the database check before you agree.

To update, say: Upgrade the hub to the new template; follow UPGRADING.md in the new release. To keep a local rule safe from updates, put it in CLAUDE.md, or in a LOCAL.md next to a skill.

Questions

Can I lose data?

Everything the database holds is also written to plain JSONL files that git tracks. If the database file breaks, it is rebuilt from them. Pruned items stay in git history.

Why not just a markdown to-do list?

A list cannot easily answer “what waits on me, oldest first” or “which ticket appears on three open items”. Lists also never forget. The database ages items out unless someone renews them.

Do the sessions run on their own?

No. A session acts when you or another session messages it. Nothing in this kit wakes an idle session by itself.

Does anything go to my tracker, chat or email automatically?

No. Outbound text is drafted for you to send.

How new is this?

The pattern (weekly calendar, durable root files) has run for months. The database is new. It has a full test suite whose tests are themselves checked by deliberately breaking the code, but it has had little time in daily use.

Getting set up: give your agent the template repo and say “follow INSTRUCTIONS.md”. It will ask you at most three questions (where the hub lives, which sessions and people, which tracker), prove the database tool works on your machine, and report back.
