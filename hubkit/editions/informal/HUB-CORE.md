# HUB-CORE.md: the shipped rules of the hub

This file ships with the hub template. **Do not edit it.** An upgrade replaces it. Put this hub's
own rules and changes in `CLAUDE.md`, which imports this file. Where the two disagree, `CLAUDE.md`
wins.

This hub is the **informal edition**: five stores, kept in plain files, git and SQLite. It needs
Python 3 and git, and nothing else. `.hub-template.json` records the edition.

## The hub exists to enable throughput

1. More solutions. 2. Faster. 3. Better quality. An agent may measure (2). The humans define (1) and (3).

The hub is read mostly by **agents**. Write for an agent that just booted with no memory: state
facts, name paths, give dates.

## What lives where

An agent that just booted looks here to know where each thing lives. The hub has five stores:

| Store | Holds | Lives in the hub | Used with |
|---|---|---|---|
| `ledger` | What needs to be done, who is doing it, what blocks what, right now. | `flow/flow.db`, with its JSONL in `flow/jsonl/` | `hubflow.py`; skill `hub-flow` |
| `memory` | What every agent must know at start: boot context, heuristics, technologies, decisions. | the root files `CLAUDE.md`, `HUB-CORE.md`, `PRINCIPLES.md`, `HEURISTICS.md`, `TECHNOLOGIES.md` | read at boot; promote into them at rotation (skill `hub-rotate`) |
| `weeks` | The raw material of each week: reports, meeting transcripts, outbound drafts. | `W0/` to `W5/`: `reports/`, `transcripts/`, `outbound-staging/` | `hubflow.py index-transcripts`; skill `hub-rotate` |
| `bespoke` | Helper scripts, skills and small stores made for this project where nothing else fits. | a tool or skill, listed in `TECHNOLOGIES.md` | the tool's own help; skill `hub-rotate` prunes the unused |
| `tracker` | The team's system of record: tickets, their criteria, events, designs, bugs. | outside the hub: a pointer such as `issue:123` in a ledger ref | `hubflow.py add --ref` |

Where each fact kind is kept. The table is generated from the design: do not edit it by hand.

### Pointers, not copies

The tracker owns a ticket's text and state; the hub holds a **pointer** (`issue:123`) and the flow
state around it. Do not copy tracker text into the hub: a second copy diverges, and nothing says
that it did. Read the tracker item again when you need it.

### What a week holds

A week holds only what people gave it: raw reports in `W*/reports/` and meeting transcripts in
`W*/transcripts/`. An analysis is a report in `W0/reports/`; what lasts is promoted into a memory
file at rotation. Code never parses a meeting transcript: an agent that reads one puts what is
needed into the ledger (open items, a `summary` row that lapses by itself), each with a
`transcript:` ref, the file name and its sha256 (`hubflow.py transcripts --files`, then `--find`
after a rotation). `hubflow.py index-transcripts W0` indexes only the Claude Code session
transcripts, and `rotate --yes` rebuilds that index.

### Outbound: staged, a human sends

All outbound text, a tracker edit too, is drafted in `W0/outbound-staging/`. A tool posts nothing,
and an agent sends nothing: a human sends.

### Bespoke tools

A tool, skill or small store an agent makes is listed in `TECHNOLOGIES.md` only if other agents can
use it for other tasks. A per-ticket helper stays with its ticket (a `file:` ref on its item). A tool
is unused when no open item refers to it and it has no listed use since the last rotation. Only
unused tools are pruned, at rotation, each with a triage decision.

### Triage and what blocks

What blocks a ticket is an open ask or thread with the ticket's `issue:` ref; `view open` lists
them. Triage is the agent's: `triage ID keep|lapse|capsule --note T` acts at once, and
`triage ID escalate --note T` leaves the item open at the top of `view open` for the human. `rotate`
lists the due items under `untriaged:` and the escalated ones under `escalated:`, and exits 0 when
each due item has a decision. `check` exits 0 when the db and the JSONL agree. Do not add `kb:`
refs: they belong to the formal edition, and hubflow treats an item with one as blocking, so only a
human can close it (`--by human --note`).

## Verify

Verify belongs to a session that did not make the work: the `review` session of `flow/seed.json`.
A hub with no review session names its verifier in `CLAUDE.md` ("Sessions"); with none named, the
human verifies, or a fresh subagent that did not make the work. The verdict is a note on the item
of the work, `pass` or `fail`, with what was checked and the evidence:

```
HUB_SESSION=review python3 .claude/scripts/hubflow.py note ID "verdict: pass: what was checked, and the evidence"
```

A `fail` names what is wrong, and the item stays open. The maker closes the item only after a pass.

## Structure: the hub is a calendar

```
CLAUDE.md                                   this hub's own rules; imports the files below
HUB-CORE.md  PRINCIPLES.md                  always in context: the shipped rules, the principles
HEURISTICS.md  TECHNOLOGIES.md              always in context: this hub's own memory files
.hub-template.json                          the template version, the edition, the checksums of shipped files
.claude/skills/                             hub-rotate, hub-flow (each may have a LOCAL.md)
.claude/scripts/hubflow.py                  the only writer of flow/flow.db
flow/                                       flow.db (ignored), seed.json, jsonl/ (tracked)
W0/ … W5/                                   the current week … five weeks back: reports/, transcripts/
```

Six weeks on disk, no more. Older weeks exist only in git history: that is the archive. Weeks start
Monday. Every week dir has a `WEEK.md` whose first line is its date range. Rotate with the
`hub-rotate` skill at the first session of the week.

Before you drop something, ask: **is it durable?** Durable knowledge is promoted out of the week
dirs (a root file or a skill), never left to roll off.

## Flow state lives in the db

Asks to a human, in-flight threads, holds and handoffs between sessions are rows in `flow/flow.db`,
written only by `hubflow.py`. Load the `hub-flow` skill before any write. Each session has an
identity (`HUB_SESSION`), set where the session is started. Named sessions are set up outside the
hub; the hub knows only their names (`flow/seed.json`).

## Shipped files and local changes

- `.hub-template.json` lists the shipped files. Do not edit a shipped file to change a rule; put
  the change in `CLAUDE.md`, or in a `LOCAL.md` next to a skill's `SKILL.md`.
- A shipped file can still be edited when there is no other way. `hubkit.py status` then shows it
  as modified, and the next upgrade merges the release into it instead of replacing it.

## Auto-memory is disposable

Write memories freely. Within one month each one is either promoted into the hub (a heuristic, a
skill, a root file) and deleted, or just deleted. A memory is never the record of a finding.

## Hard rules

- Commit the hub at natural stopping points without being asked. Stage explicit paths, never
  `git add -A`. Commit with a pathspec (`git commit -m … -- <paths>`), so a peer session's staged
  files do not ride along.
- Outbound text is staged in `W0/outbound-staging/`, never sent by an agent. A human sends.
