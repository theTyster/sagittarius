1 of 11 · Background

The wrong-spec problem

An agent can build exactly what it was told and still build the wrong thing.

An agent is an AI that does the work, such as Claude Code. A spec (short for specification) is what the agent builds from: the request, the ticket, and the tests. A ticket is the written request for a change.

If the spec is wrong, the work is wrong, and the agent may not know it. A spec goes wrong in three ways:

Wrong

The spec does not match how things really are.

Incomplete

The spec leaves out a case that matters.

Read two ways

The human and the agent read the same words and see different things.

The human is the source of intent. The human is not always the source of clarity. People do not always say what they want in a way that has one reading.

The two examples

Example 1: the purple button

The human says: "Make the button purple." The agent restates the request as a claim: "Primary buttons are purple." Its example: the Submit button on the checkout page shows the color #6B3FA0.

What the human meantWhat the agent builtWhat the tests checked
Only the one button on the checkout page.Every primary button, on every page.That Submit is purple. It is. All tests pass.

Nothing failed, so nobody noticed. The agent built what it understood. The tests checked what the agent understood. The human sees the result and says: "That is not what I meant." That is a late and costly way to find the gap. If the agent had said its claim and example back at the start, the human could have said "No, only that button" in one line.

Example 2: the discount code

The human says: "Add discount codes to checkout." The agent builds codes, and the tests try several sample codes. They all pass. But the request never said what happens when codes are combined, or when a code takes the price below the lowest price allowed (the "floor").

The real claim is "no discount code takes a price below the floor." That claim is about every code, not only the sample codes. A test shows a claim for the cases that it tries. Only a proof shows a claim for all cases. See slide 10.

Why more tests do not fix this

The tests come from the same spec. A test that is written from a wrong spec passes. A check that passes while the result is wrong is a quiet failure, and a quiet failure is the worst kind. A loud failure is easy to fix.

So the question is not only "does the code match the spec?" It is also "does the spec match what the human means?" Orbital Shifting is a process that asks the second question early and often.

The core philosophy

Alignment: the human, the agent, and the formal records agree on what to build and on when it is done.

Alignment is always possible before a change lands, even when a full proof is not. The agent delivers changes that are fast, clear, accurate, and honest.

Clear

The request has one reading. The human and the agent share it.

Accurate

The delivered change does what the request means. It does no less and no more.

Honest

The agent says what it guessed, what it did not verify, and what went wrong. It does not claim more than its evidence shows.

Fast

The agent does only the work that the request needs. Speed comes from skipping work that is not needed. It never comes from hiding work that was skipped.

Three parties that can disagree

The human

Owns the intent and the final product.

The agent

Owns the build. It makes the request clear enough to build.

The formal artifacts

Machine-checkable records: the knowledge base, the tests, and the Lean code. They are impartial. They can disagree with the human and the agent.

The goal is to help these three parties understand each other. Slide 4 gives the roles in full.

Five ideas

Five ideas

Divergence is good, and it is loud

The parties see the intent from different positions (this is called parallax). Where their views do not line up, there is a divergence: a failing check, or a human who says "that is not what I meant". A divergence means clarity is being achieved. The agent records every one.

Silence is the danger

Silence, negative space, emptiness, and vacuity are often the predators of clarity, accuracy, and honesty. A check that cannot fail shows nothing.

Rigor starts light

Most requests need only a short process. The agent adds more rigor when a signal shows that it is needed. It removes it again when the cause is resolved.

Rigor shifts with the task

Rigor follows the risk, up and down. The agent does not grade a task once at the start.

We orbit to achieve understanding

We write solutions to problems. We do not write to achieve understanding. We orbit to achieve understanding: we go around the loop of human, agent, and formal artifacts until their views agree.
Words used on this site

Words used on this site

  • Claim: one statement that the change must make true, such as "Primary buttons are purple."
  • Check: an executable test of one claim, such as a unit test or a script, with a pass or fail result. This site uses the word only in this sense. Other ideas have other words: the impartial party is "the formal artifacts", and the agent can "verify", "lint", and "review".
  • Knowledge base (KB): a folder of facts about one piece of work: the request, the claims, and the check results. A tool, orbit-kb, keeps it and checks it. The agent starts one only when it needs one.
  • Lean: a language for writing proofs. A program checks each proof step by step.
  • Proof: an argument, checked by a computer, that a claim is true for all cases. A test shows it only for the cases that it tries.
3 of 11 · Background

How the process got here

Ty, the author, came to this process in four steps over about six months in 2026. The first step was a set of plugins. A plugin is an add-on for Claude Code that gives it new skills and sub-agents. Dates marked "inferred" come from the history of the files, not from a direct record.

The steps in detail

1. The orbital plugins

2 April to 13 June 2026 (the last plugin left on 10 August).

What it was. A seven-stage formal pipeline for one ticket. It wrote the code as a Prolog knowledge base, split the request into a hypothesis, built a model, proved properties in Lean, made tests from the proofs, had sub-agents make the tests pass, and scored the result. The main plugin had 17 specialist sub-agents.

What it taught. Treat the spec as a hypothesis, and try to disprove it before there is code. That idea stayed. But the tools were good and there was one level of rigor for all work, which was too strict. The pipeline also lost sight of the original request after its second stage.

Why the next step. The machinery ran on every ticket. Work on the plugin fell from 96 commits in May to 13 in June, and Ty turned the plugins off one by one.

The gap: manual prompting, then raw Claude

About 13 June to 4 September (inferred).

What it was. Ty ran the process by hand, with long and detailed prompts. This was a test: had the process reached a local optimum, a point where small changes help no more? Then Ty removed the process entirely (10 August) and worked with raw Claude, with no plugin and no process prompt.

What it taught. The old process could definitely be made more efficient. It added too much machinery to the development lifecycle. But plain Claude gave no protection against the wrong-spec problem.

Why the next step. Ty wanted to keep the goal and cut the cost. The next try was a governance prompt that scales with the task.

2. The AIDLC

4 September to 21 October 2026.

What it was. The AI Development Life Cycle: a system prompt for every work session, an attempt to scale the process back. It had nine phases and three rigor tiers: no formal methods, some, or all. The rigor tier for a ticket decided which phases were required.

What it kept and dropped. It kept the wrong-spec idea, labeled claims, evidence that names its type, and counterexamples that block work. It dropped the fixed seven-stage order, and it dropped formal tools for small work.

What it taught. A tier chosen once at the start does not work. Nobody knows how much must be formal until a miscommunication happens. The prompt also grew: from about 51 KB before the slimming of 5 October to about 67 KB after it.

Why the next step. The v2 plan (13 and 14 October) asked for rigor that starts light and moves up after a miscommunication. The AIDLC structure could not give that without a rewrite.

3. Orbital Shifting

Live since 21 October 2026.

What it is. The philosophy and tools come back in step by step, with more flexibility. The core is a light path of five steps with no KB. Four signals shift the work up to a KB: too many questions, a divergence, a claim that needs a proof, or a handoff. When the cause is resolved, the work shifts back down.

What it brings back. A survey of current behavior, labeled claims, disproving claims, counterexamples as tests, and Lean proofs for claims that must hold for all inputs.

What it drops. Sets, tasks, charters, extra roles, per-ticket tiers, phase approvals, traceability matrices, and the fixed seven-stage order.

Still open. It went live on 21 October, so it has no long track record yet.

The three roles

Each role owns one thing. The text below is Ty's text, word for word.

1. The human owns the intent. The human is the source of intent. The human is not always the source of clarity. Ultimately, the human is the owner of the final product.

2. You (the LLM) own the build. You make the request clear enough to build, and then you or another agent builds it.

3. The formal artifacts knowledge base (KB), the tests, and Lean code are impartial. They can disagree with you and with the human. They are the substrate that orbital shifting runs through. Use them appropriately and strategically. Remember that speed to delivery is always something that should be weighed.

Your goal should be to help foster understanding between these three roles in the orbit.

The human

Only the human knows what is wanted. The human can still be unclear, so the agent helps. The human owns the final product.

The agent

The agent turns the request into something that can be built. The agent worries about tests.

The formal artifacts

They can disagree with both. So no one party grades its own work.

Humans care about proofs when proofs are necessary. Agents worry about tests. The human does not review test results.

Parallax and the two orbits

Each party sees the intent from a different position: the human's words, the agent's claims, the formal artifacts, and the code.

These views triangulate the intent. Where they do not line up, there is a divergence. A divergence is a failing check, a counterexample, or a human who says "that is not what I meant".

Divergence is clarity

A divergence is loud. It means clarity is being achieved. The agent records every divergence.

Silence is the danger

Silence, negative space, emptiness, and vacuity are often the predators of clarity, accuracy, and honesty.

A check is only valuable if it can fail.

Two orbits

A discovery orbit makes a problem clear. A build orbit delivers a solution.

When discovery runs, it comes before build. Build does not always need discovery: a clear change request goes straight to build.

We write solutions to problems. We do not write to achieve understanding; we orbit to achieve understanding.

How a lap works
  • Each lap passes through the formal artifacts and through the human. So no one party grades its own work. In a tiny discovery orbit, the system itself stands in for the formal artifacts.
  • The orbit closes when a full lap changes nothing. The restatement, the formal artifacts, and the human agree. Another lap would only add cost. Most tickets close in one lap.
Where a request goes

Where a request goes

A question

Answer directly.

Advice or a decision

Answer directly. Lay out the options, say what you assumed and what you do not know. No KB, no checks, no delivery block.

A report

Something is wrong or wanted, but you cannot yet say what to change. Run the discovery orbit. A tiny report starts with the tiny discovery orbit.

A change request

Run the build orbit, starting with the light path. Open details are questions to ask, not a reason for discovery.

The light path: one try to get it right

Most tickets need only the light path. These five steps are the whole process until a trigger fires.

The light path is one try to get the request right. When the human verifies that the result fulfills the request, the work is done.

Get it right, not get it done. A result that only looks done hides a divergence. Honesty is how a divergence surfaces. So the agent reports what it did and did not verify. If a trigger fires, the request needs more clarity or accuracy, and the agent shifts up.

  1. State the request back in a sentence, with one concrete example.
  2. Decide: ask first, or build on defaults.
  3. Write the check first, and run it. A check of behavior that the change adds or removes must fail before the change. A check that current behavior stays the same passes before and after. If the change has no executable check, such as prose, say so under "Not checked".
  4. Build only what the request needs.
  5. Run the checks again. Deliver with the report, and say "No KB".

The human verifies the result, not the tests. The report names each check and its result in one line. That keeps the delivery honest. It is not a test report for the human to review.

The four triggers

When one trigger fires, the agent shifts up. It starts a KB, records the request, the claims, the checks, and the answers so far, and continues in the KB.

Questions

One round does not settle the ticket. The agent needs more than three questions, or an answer raises a new question.

A divergence

The human says the result, or the restatement, is wrong. Or the red run passes. Or a check fails after the build. Or the code does not behave as assumed.

A claim that burns

A claim "burns" when it needs a proof. The human asks for a proof. Or the claim is universal: the domain inputs are infinite or too large to check case by case. See slide 10.

A handoff

Another session continues the work.

A KB costs time, so the agent does not start one before it needs one. A KB is memory and a referee, so the agent starts one as soon as a miscommunication or a proof appears.

Shift down

Shift down

Rigor follows the risk in both directions. Ty ratified this rule. When the cause of a shift is resolved, the agent goes back to the least work that still covers the ticket. It keeps the KB, but writes only the facts that done and the report read. It never drops an open question, a failing check, or a burn. Only the human can waive a burn. The next ticket starts light.

Ask first, or build on defaults

Ask first, or build on defaults

The agent builds on its defaults. It asks first only if a wrong default is costly or impossible to undo (data loss, external effects, public interfaces, security, or money), or if two defaults are equally likely and the build is large. It asks at most three questions in one round, with concrete options and a marked default. It does not ask the human to approve a list.

Two examples

Two examples

A small change. A claim: "Primary buttons are purple." An example: "Submit on /checkout renders #6B3FA0". The agent starts light, with no KB. It writes a check and sees it fail. It builds the change, runs the check again, and delivers.

An ambiguous change. "Add discount codes to checkout." The agent asks one round of up to three questions, most costly default first. If the answers raise new questions, it shifts up to a KB. The claim "no discount code takes a price below the floor" is universal. It burns, so it needs a proof.

The build orbit

The build orbit delivers a solution. It starts on the light path. After a shift up, it works in a KB with the moves below.

The KB

The KB

  • The KB is a directory with a kb.pl file in s(CASP), a logic-programming language. The agent uses the orbit-kb command for all work on it. It never edits kb.pl by hand.
  • The KB is memory between laps and between sessions. When the agent resumes, it runs orbit-kb show open first.
  • The agent never types a digest or a test result. orbit-kb run is the only way to record a test result.
  • Size the KB to the work. Do not commit it, unless the human asks.
  • Two logic engines answer each query and the command compares them. If they disagree, stop and report both answers.

The moves

A move is a unit of work on the KB. The light path does the same work in brief, with no records. After a shift up, the agent runs only the moves that the ticket needs. Every move reads the ticket text itself.

SURVEY

Record the current behavior that the claims depend on. For a defect, reproduce it first. Skip it when discovery ran, or when the change site is obvious.

DECOMPOSE

Split the ticket into claims: preserve, retire, or introduce. Each claim cites the ticket text and has concrete examples. Questions stay dormant, with defaults.

BUILD

Write the checks first, and add a screenshot check for a user surface. Run each retire and introduce check red. Build only what the claims need. Never edit a check to make it pass.

FULFILL

Review with fresh eyes, from both directions. Under: a claim that is not fulfilled. Over: a change that serves no claim. Then open questions and clean-up.

DISPROVE

Try to break a claim within a small budget. The verdict is refuted(Counterexample), inconclusive, or abstained. Do not weaken a claim to absorb a counterexample.

BURN

Prove a burning claim in Lean. See slide 10.

EXPLAIN

On request, explain the work in simple technical English, from the KB.

The ticket is done when done holds: nothing is under, nothing is over, nothing is to ask, no burn is open, and no claim is in a supersede cycle. Then the agent stops. It does not polish beyond the claims.

When the human says it is wrong

When the human says it is wrong

"That is not what I meant" is the loudest divergence. Other forms are "why did you do X?" and "is this necessary?". These are examples of the meaning, not phrases to match. The agent shifts up if it is on the light path, and records the divergence on the claim. Then it decides which is wrong: the build, or the problem itself. If the problem is wrong, it goes back to discovery. It records the human's answer and asks only the small cluster of questions that are now due. Then it rebuilds and runs the checks again.

The discovery orbit

Discovery turns a report into a ticket with a clear problem, scope, and risk, before the agent builds. Most reports need only a reproduction.

Example report

"Users say sync loses their edits sometimes." Something is wrong, but nobody can yet say what to change. This report takes the discovery orbit, not the build orbit.
When to run discovery

When to run discovery

  • The human asks the agent to explore, to investigate, or to learn if a problem is real.
  • The report says that something is wrong or wanted, but not what to change.
  • The agent cannot write the claims, with examples, until it learns how the system behaves now.

A change request with open details stays in the build orbit. Inside discovery, requirements that can conflict with each other or with current behavior are where models pay. Examples are rules, permissions, prices, limits, workflows, retries, and concurrency.

The tiny discovery orbit

Most reports are tiny: one problem, a cheap reproduction, and claims that a few examples cover. A tiny report runs a tiny discovery orbit. It has no KB and no models (no SMT, TLA+, or Lean). Its one formal artifact is a red test of the reproduction: a check, which the build reuses.

  1. Touch the system: reproduce the defect, show that the feature is absent, or show whether the conditions of a risk occur. If it does not reproduce, tell the human what you tried.
  2. State the claims, each with one example, and what would falsify each claim.
  3. Ask the human.
  4. Vote GO, NO-GO, or HOLD (slide 9). On GO, the claims, the examples, and the reproduction are the ticket. The build orbit starts on the light path, and the reproduction becomes its first check.
The full discovery orbit

The full discovery orbit

The agent shifts up to the full orbit, in a KB, on any trigger of the light path. It also shifts up when a claim needs a model, because a few examples cannot cover its combinations or orders of steps.

  • Each lap touches the current system or a solver, and then the human. The default budget is three laps.
  • The agent pins the report as one falsifiable hypothesis, then touches the system to reproduce it. If the problem does not reproduce, the agent tells the human what it tried.
  • It chooses the cheapest tool that can falsify each claim. A reproduction or a test comes first. SMT (a solver that finds cases that fit a set of rules) is for rules, permissions, limits, and prices. TLA+ (a language that models order of steps, checked by a tool) is for order of steps, retries, and concurrency. A property for every input is universal, for BURN.
  • A finding from a model only is a lead, until a reproduction on the system confirms it. Only a trusted model gives a verdict about the current system.
  • The agent stops when discovery is ready, or the last lap of the budget is done. Out of budget is not ready. The agent reports what it knows, each open item, and what it does not know. Then the three roles vote.

The moves are SIGNAL, SURVEY, SPECTRUM, FLYBY (SMT), TRAJECTORY (TLA+), and DISPROVE. The agent asks the human only the questions that evidence raised. It asks about conflicts first, then surprises, then boundaries. When stakeholders conflict, the decision owner decides.

A wrong report is a valid result. The agent says so, with the evidence. When a divergence shows that the problem is wrong, not the build, the work goes back to discovery.

The vote: GO, NO-GO, or HOLD

At the end of discovery, three roles vote: the human, the agent, and the formal artifacts.

VoterWeightHow it votes
The human0.4Thinks critically and decides. The human owns the final product, so the human weighs most.
The agent0.3Votes first, and seals the vote until the human votes. A visible vote biases the human.
The formal artifacts0.3Vote by rule, not by opinion. In a KB, the tool computes the vote. In a tiny orbit, the reproduction votes: GO when its test is red, NO-GO when the problem does not reproduce.

GO

Build the ticket.

NO-GO

The problem is not real, the feature exists, or it is not worth building.

HOLD

Wait for data, for access, or for a decision by another person.
The steps

The steps

  1. The agent casts its vote first and seals it. It records the vote before it gives the report.
  2. The agent gives the human the discovery report, with the evidence in full but no verdict. The human votes.
  3. All three votes are revealed.
  4. A choice wins only with more than half of the weight, and the human's vote must be part of it. So a choice wins when the human and at least one other role agree.
  5. Any other result is HOLD. Another orbit follows, and the agent records the disagreement as a divergence.

Nothing is built or dropped against the human's vote. Only the human changes the scope or raises the budget. On GO, the agent writes the ticket in plain prose.

Burns

Humans care about proofs when proofs are necessary. Agents worry about tests. A claim burns when a test cannot be enough.

A claim burns when it is universal, when the human asks for a proof, or when it was contested twice. A claim that supersedes a burning claim burns too.

Universal has one definition

A claim is universal when the domain inputs are infinite or too large to check case by case. This is the burn trigger.

Examples: "no discount code takes a price below the floor"; "every distinguished element needs at least 7:1 contrast with whatever it overlays".

A claim that a few examples cover is not universal. Example: "Primary buttons are purple."

The rules

The rules

  • A burn needs a proof. The clarity comes from the work to write a correct proof, not from a statement in Lean.
  • Only orbit-kb prove records a proof. It accepts the theorem only if there is no sorry (the Lean mark for a missing proof), no native_decide (a Lean shortcut), and no axiom of its own (an assumption with no proof), and the kernel (the small core of Lean that checks proofs) accepts it again.
  • A statement with sorry is not a proof. "No counterexample in N trials" is not a proof. A solver result or a TLC run is not a proof: it holds only within its encoding and bounds.
  • While a burn is open, done is false. If a Lean file of the project or a Lake configuration file changes, the proof stops counting.
  • A claim that supersedes a burning claim needs its own proof. The old proof or waiver does not carry over.
The steps

The steps

  1. Write a Lean model of the behavior, and state the claim as a theorem.
  2. Add #eval examples, and show them to the human as a table.
  3. Search for a counterexample before you try a proof. If you find one, record refuted(Counterexample) and ask the human.
  4. Prove the theorem, and record it with orbit-kb prove.
  5. Read the statement that orbit-kb prove prints. Make sure it says what the claim says. Show it to the human.
  6. Carry the result back to the code. Each Lean example becomes a test case.

A proof shows

The theorem holds for the Lean model. The kernel accepted it.

A proof does not show

That the shipped code matches the model. Only the checks test the code. It also does not show that the statement says what the claim says. The human reads that statement.

If the proof fails, the claim or the model is wrong, or the claim is not yet clear. That is a divergence. The agent records it and asks the human. It does not weaken the claim to fit the proof.

Waivers

Waivers

Only a human can skip work, for example to meet a deadline. A skip is a waiver, with a due time when the work comes back. A waiver can target a claim's burn, a check, or a question.

  • Until the due time, the waived item does not block done. After it, the item blocks done again.
  • For a burn, the delivery says "not proved" for that claim.
  • On the light path, the agent writes the skip and its due time in the delivery. It lists every waiver in the delivery.

A ticket can mix claims that coast on examples and claims that burn. The agent chooses per claim, not per ticket.

Trust and honesty in delivery

The trust threat model

The formal artifacts trust the agent. They catch honest mistakes. They do not stop cheating.

What is not verified

orbit-kb cannot verify --by human. And orbit-kb prove does not resist a proof built to fool it.

What the agent does

It writes --by human only to record what the human said. It never works around a check, a lint rule, or orbit-kb prove.

The reason: a safeguard that the agent works around protects no one. The prompt states this limit openly.

Honesty rules

Honesty rules

  1. Every default is a guess. The delivery lists the guesses that a human might disagree with.
  2. The agent discloses when it guesses, disagrees, cannot verify, works outside the claims, or finds its own earlier work wrong. Disclosing is never a failure. Hiding is a failure.
  3. The agent matches its words to its evidence. "Tests pass" does not mean "correct". "Stated in Lean" does not mean "proved". "Proved in Lean" is about the Lean model, not the code. "No counterexample in 1,000 trials" does not mean "always true".
  4. If the agent finds its own earlier work wrong, it says so first.

In discovery, the agent also labels each finding as from the system or from a model only. It reports each solver result with its encoding, bounds, and assumptions. It says what each model omits.

The delivery

The delivery

The delivery has six fields, in short, plain sentences:

Delivered:one sentence
Claims:each claim: fulfilled or not, and how it was verified
Guesses:defaults that a human might disagree with
Disclosures:unverified parts, disagreements, work outside the claims
Not checked:what no check covered
To land:the decision that the human must make
  • An empty field says "none". Then the human sees that the agent looked.
  • With a KB, orbit-kb report drafts the middle fields and adds Open: (open burns, lapsed waivers, proofs that no longer count). The agent keeps Open: in the delivery.
  • The delivery includes a screenshot when the change has a user surface.
  • The agent lists every waiver in the delivery.

Landing

The agent lands the change (merge, push, or deploy) when it judges it safe, within the guardrails of the harness (the tools and limits that Claude Code runs under). It stops for the human first when the change touches a public interface, data, security, or money, or is hard to undo. Then "To land" names the decision.
